# 版本与发布

目标版本与实际线上版本分开记录。机器可读状态：[state.json](state.json)；当前版本计划：[0.1.0/PLAN.md](0.1.0/PLAN.md)。

## 版本规则

- 所有需求、任务、交付、验证和发布使用 `x.y.z`。
- `targetVersion` 是当前工作目标，不等于已发布版本。
- `onlineVersion` 只记录实际可用、已确认的线上版本；没有正式产品发布时必须为 `null`，不能填 `0.0.0`、`0.1.0` 或猜测值。
- `onlineTag` 只记录实际存在的发布 tag；未发布时为 `null`。
- 同版本内可按功能点连续交付；当前版本上线前，下一版本只准备需求，不进入当前接收条件。
- 待合并 MR 的源分支只接收本批交付的修正。

## 发布流程（`ops → main`）

1. **接收候选**：ops 一次只接收一个候选；候选包含版本、构建身份、test 的验收结论、未满足项和回退方式。
2. **发起 PR**：ops 发起 `ops → main`，按协议组织独立审核；main 的授权接收者检查接收条件。
3. **发布同一构建产物**：不重新构建后再发布不同产物；发布/部署使用候选身份对应的同一构建。
4. **确认可用**：确认目标环境实际可用，记录执行链接或实际观察；未确认不得登记线上版本。
5. **合并并登记**：授权接收者以 merge commit 合并；更新 `state.json` 的 `onlineVersion`、`onlineTag`、`status`、`releasedAt`，并在发布记录写版本/构建/验收链接。
6. **失败处理**：发布失败保持原线上版本和原 tag，不把候选写成已发布。发布成功但合并失败时，完成记录同步或回退；不得留下静默不一致。

## 首个正式发布前

当前 `targetVersion=0.1.0`，`onlineVersion=null`，`status=unreleased`。本轮七管线治理合并到 `main` 只是治理基线集成，不创建发布 tag，也不把 `main` 写成“已上线 0.1.0”。首次正式上线前，所有文档必须明确“无线上版本”。

## 发布后基线同步

正式发布后允许 `main → pipeline/*` 的基线同步 MR，由接收管线合并，吸收线上修复并保留各自目标版本。同步不是功能交付；不得把新功能夹带进基线同步。

## 发布记录最小字段

- 版本 `x.y.z` 与 tag；
- 构建身份（commit、构建配置/产物摘要）；
- test 验收结论链接；
- 未满足项；
- 发布/部署执行链接；
- 实际可用确认；
- 回退版本与回退方式。
