# 管线交互协议

版本：`0.1.0`。本协议适用于全部固定管线和 `main` 集成。

## 1. 分支与工作区

1. 只在 `pipeline/<name>` 所属固定分支提交；分支与工作区对应见 [总表](README.md)。
2. 固定分支建立后禁止新增分支、删除分支和强推。旧 `task/*` 分支只读，不再接收新提交。
3. 每个管线使用独立工作区并启用 sparse-checkout，只显示本管线文档、共享协议和必要契约。
4. 管线内提交可由本管线直接完成；跨管线必须通过 MR。`main` 只接收 `ops → main`。

## 2. MR 前置条件

上游发起 MR 前必须：

- 工作项带目标版本 `x.y.z`，并与 `spec/releases/state.json` 的 `targetVersion` 一致；
- 只包含本批交付的提交；源分支不夹带下一版本或无关整理；
- 运行与改动相符的验证，并把最新结果写入 PR 正文；
- 指定与本批交付无作者关系的独立审查者；审查者检查实际 diff、验证证据和未满足项，不能只重复作者结论；
- 旧审查结果可复用，但只限未变化的提交；新增或修改内容必须补充审查。

下游接收前必须检查：版本、工作项、交付内容、接收条件、验证证据、未满足项，以及上游独立审查结论。未满足接收条件时，在原 PR 讨论/验收条目中反馈，不合并，也不另建平行结论文件。

## 3. PR 正文（只保留五项）

PR 正文使用 [模板](../../.github/pull_request_template.md)，只允许以下五个二级标题，不添加其他二级标题：

```markdown
## 目标版本与工作项
- 版本：0.1.0
- 工作项：...

## 交付内容
...

## 接收条件
...

## 最新验证
...

## 未满足项
- 无；或逐条列出未满足项、责任管线和下一次验证入口。
```

`Submit-PipelineRequest.ps1` 会拒绝缺少字段、版本不符或多余二级标题的正文。

## 4. 发起、审查、接收

```text
上游提交 → 上游独立审查 → 发起上游 MR
        → 下游检查接收条件 → 下游 merge commit
        → 源分支保留 → 下游继续正向交付
```

- 上游是交付作者，负责在源分支修复问题。
- 下游是接收者，负责检查条件并合并；不能替上游静默修改交付。
- 审查讨论和验收条目留在原 PR；修复后在原 PR 更新最新验证。
- 合并使用 merge commit，保留功能提交；禁止 squash 和 rebase 改写公开历史。
- 合并后不自动删除源分支。分支删除由规则集禁止。

### 旧 task 分支迁移例外

已批准的一次性迁移可以把旧 `task/*` 历史并入 `pipeline/tech`，但迁移 merge commit 的净 diff 必须落在接收管线所有权内；只对 `Scripts/Collaboration/pipelines.json` 中 `legacyTaskCommits` 明确列出的提交免除逐提交重新归责，不按现存 task ref 动态放行。迁移完成后删除旧 task 分支和工作区，该列表不再适用于新交付。非法改写、未审查的旧提交或净 diff 越界仍不得接收。

## 5. 管线交付说明

- `tech → art`：技术提供接入规格、定稿文本或文本版本、制作要求和验收方式；`art` 据此制作源素材。
- `art → tech`：美术/声音交付源素材、来源与加工记录、导入清单；UE 二进制资产由 `tech` 唯一导入和写入。
- `tech → test`：技术交付已集成的可运行成果、构建/用例身份和已知限制；测试不得用未集成分支或零用例替代。
- `growth → narrative/tech`：需求范围、验收条件和工作项版本先明确；剧情文本由 `narrative` 定稿后再进入技术导入和批量素材制作。
- `test → ops`：验收结论必须引用实际执行链接；未满足项随候选一起交付。
- `maintenance → ops`：维护分支保持在当前线上基线；线上修复与维护候选一起交付，由测试直接验证候选或其构建产物。
- `ops → main`：运营一次只接收一个发布候选，发起并组织审核；授权接收者合并后登记线上 `x.y.z`。

## 6. 版本与发布

- 正常交付链中的剧情、技术、美术、测试和运营围绕同一待发布版本推进；同版本内可按功能点连续交付。
- 当前版本上线前，下一版本只准备需求，不并入当前实现。待合并 MR 的源分支只接收本批修正。
- 发布成功后更新 `main`：运营接收已验候选、发起并审核发布 PR、发布同一构建产物、确认实际可用，再由接收方合并并登记线上 `x.y.z`。
- 发布失败保持原线上版本。发布成功但合并失败时，完成记录同步或回退，不能留下“已发布但无记录”的静默状态。
- 首次正式上线前，`onlineVersion` 保持 `null`，不得用目标版本冒充线上版本。

## 7. 角色边界与升级

- 跨管线接口修改先由需求/技术在 MR 中写明影响、失败/取消行为和验证；受影响管线评审自己的端点。
- 文件或工作树已被他人改动时保留内容并核对，不强制重置或清理。
- 超出现有授权的不可逆操作、正式发布、其他仓库或远端服务，不在本协议内自动执行。
