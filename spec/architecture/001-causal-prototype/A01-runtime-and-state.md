## 本项确认范围

已确认采用 **UE5 单机、单进程、按职责拆分的架构，C++ 管理核心规则，蓝图组织场景表现；当次世界状态与持久实验日志分离**。

本项决定总体运行方式、代码分工、数据所有权和模块通信方式。具体引擎版本、输入、AI、战斗判定、球体运动、砍树几何、雨火演进、跳时结算和日志字段后续逐项确认；图中的模块表示职责，不要求各建插件或独立工程。

## 数据归属

1. **配置资产**保存初始状态、调参值和预设内容，不被当前游玩改写。
2. **各玩法模块**拥有角色、敌人、树木等当次运行状态。实验协调器不再维护一套相同的生命值或燃烧状态。
3. **实验协调器**拥有本轮阶段、是否发现现场、使用过的救助类别、各计时起点和因果结果，依据玩法模块提交的事实推进流程。
4. **表现层**读取状态、播放反馈并提交操作意图，不自行判定救援成败。回访对话进度是完成条件的输入，由流程逻辑最终裁定。
5. **日志模块**保存结果记录，不参与世界状态回放；不增加存档续玩功能。

## 数据流

1. 开始一轮时，由初始配置复位世界与流程状态；遇险事件和降雨计划从世界运行时开始推进，不能等待玩家输入。
2. 玩家输入转为动作请求，交给角色、战斗或其他相应玩法模块。模块按规则改变自身状态，并发出类型化事实。
3. **动作事实和命中事实分开**：发现遇险后使用剑术或魔法即计入方式；首次朝哥布林攻击即开始救援计时并触发转移目标；伤害仍须有相应命中依据。发现现场、开始攻击和世界启动是三个独立起点。
4. 协调器消费事实，判定阶段与结果。成功后先把必要的环境变化纳入结算，再构造 30 年后的回访；即使救援提前结束，预设降雨仍须影响结果。中间演进算法另项确认，不能直接忽略雨火后果。
5. 失败按需求规定时点结束：未发现前小孩已死时，要等玩家发现后果再结束。只有成功路线进入教师回访。表现层不提前泄露因果分支。
6. 成败均产生独立日志记录，保存方式、分支、原因及三个阶段实际耗时；未进入的阶段标为未发生，未开始攻击的救援计时标为未开始。
7. 用户手动重启后，各模块和协调器回到初始状态，旧日志保留。使用同一实验地图和配置，不为每次尝试生成永久世界副本。具体复位、旧回调清理与写入失败处理在日志复测项确认。

## 原因与取舍

- 单玩家和约十分钟的验证流程适合单个 UE 进程，部署与调试成本较低。本轮不引入服务器、数据库或消息中间件。
- C++ 便于集中核对跨模块规则和状态；蓝图便于调整灰盒、资源、台词与反馈。相较纯蓝图，增加 C++ 编译准备成本；收益是复杂规则更易检查和维护。
- 唯一状态归属减少“画面里小孩死亡，但流程仍判成功”之类的分歧；类型化通知让战斗、环境、回访不必直接改写彼此的内部数据。
- 日志与运行状态分离，能满足“重置世界但保留实验记录”；文件日志足以支持本轮比较，不需要事件溯源或数据库。
- 只做职责拆分，不搭建通用社会模拟框架。以后做多人需要重新审视网络权威、同步及持久化；本方案不宣称已经具备多人能力。
